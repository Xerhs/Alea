# Audit status

`SPEC.md` §32 lists `AUDIT-STATUS.md` as one of the fixed files every
stable release archive contains. `SPEC.md` §36.2 defines the "minimum
credible gate set" — "the floor below which no build may drop the
experimental label under any future revision of this specification."
This document reports Alea's status against that floor, bullet
by bullet, honestly, as of this writing. It is a status report, not a
release announcement: an unmet bullet below does not mean "coming soon
in the next release," it means the project has not yet done the work
(or found the external party) that bullet requires.

This file *is* `docs/audit-status.md` — the file `SPEC.md` §9's repo tree
names and `IMPLEMENTATION_MAP.md` assigns to WP-35 ("Adversarial review
sweep... Output: the §36.2 evidence table"), independent of the rest of
`docs/` (WP-36, per `docs/README.md`). It serves two purposes at once:
the §36.2 gate-by-gate table immediately below, and — in "Targeted
spec-conformance sweep findings" further down — a running log of specific
MUST-level findings and their fix/residual status as individual
conformance sweeps turn them up, ahead of a full WP-35 review. At release
time, the current content of this file is what gets copied into the
release archive root as `AUDIT-STATUS.md` (`SPEC.md` §32's fixed release-
archive file list uses the release-artifact naming convention shared with
`SHA256SUMS`/`REPRODUCING.md`-at-repo-root; the underlying content is the
same document, not a second one).

`SECURITY.md`'s `EXPERIMENTAL SECURITY SOFTWARE` banner reflects exactly
this and MUST remain active until all eight rows above read **Met**.

## What is mechanically re-checkable right now

Rows 1, 2, 4 and 6 above are backed by tests that run in this
repository's own CI via `ci.sh`'s `cargo test --workspace` step. Row 5's
suite (`tests/fault-injection/`) and the §29.6 leakage suite
(`tests/leakage/`) are deliberately standalone Cargo workspaces — not
root-workspace members — so `cargo test --workspace` never reaches them;
`ci.sh` runs each explicitly by manifest path
(`cargo test --manifest-path tests/fault-injection/Cargo.toml`, and
likewise for `tests/leakage/`). Anyone can re-verify all five rows by
running `ci.sh` rather than trusting this table. The distinction is
load-bearing, not pedantry: before 2026-08-06 nothing executed the two
standalone suites at all, they had silently stopped compiling against
API drift, and row 5 read "Met" on the strength of a suite no automation
ran. "Mechanically re-checkable" in this document means: executed by
`ci.sh` on every run, with a compile failure counting as a CI failure.
Rows 3, 7 and 8 are inherently not something in-repo tooling can satisfy
on its own: they require an independent party, a funded external
reviewer, and a real multi-person signing history respectively. Tooling
in this repository (`tools/release-verifier --check-manifest`,
`tools/image-builder`'s `sbom-gen`/`denylist-gen`/
`entropy-policy-export`) exists to make satisfying rows 3 and 8
*mechanically checkable once the organizational side happens* — it
cannot manufacture the organizational side itself.
