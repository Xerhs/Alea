Air-gapped · Pre-OS · Open source

Generate your Bitcoin recovery words before any operating system loads.

Alea is a small UEFI application that boots from a USB stick and creates a standard BIP39 seed from entropy you chose — physical dice, coin flips, an approved hardware random source, or a mix — with the ordinary desktop OS removed from the process entirely.

It is not "memtest for seeds." Alea is specified to refuse virtualized platforms, remote-console paths, managed endpoints and hardware it cannot reason about — and to tell you why. Refusal is a feature.

What Alea is — and is not

A boot tool that completes the seed ceremony on a vetted subset of machines, and loudly refuses the rest.

Alea reduces what you have to trust for seed generation by removing the general-purpose operating system from it. It does not remove the motherboard firmware, the CPU, memory, the display hardware, your physical environment, the compiler, or the release process from what you are trusting — and it says so, plainly, on screen and in every document.

  • Standard BIP39. 12 or 24 words that restore into Trezor, Ledger, Coldcard, Sparrow, Electrum, BlueWallet — any BIP39 wallet. There is no "Alea seed"; you generated a seed.
  • Your entropy, your choice. Dice, coins, an approved machine source, or a combination — with the physical transcript recorded so you can independently reproduce the result.
  • Confirm before you fund. After full re-entry it shows the master fingerprint and first receive addresses so you can check your signing device restored the exact same wallet before depositing.
  • Reproducible & verifiable. An independently-written Python reference implementation and a frozen test-vector corpus let anyone check the math bit-for-bit.
  • Not a hardware wallet, not a secure element, and not proof your computer is trustworthy.
  • Not universal — it refuses hypervisors, remote consoles and hardware it cannot classify, on purpose.
  • Never shows or exports a private key, xprv, or the raw seed.

The ceremony

Deliberate, slow, and reboot-based — because that is the cost of the trust reduction.

Prepare & check the machine

Acknowledge what you are and aren't trusting, confirm this is the machine's own physical display, and pass the device self-tests.

Choose your entropy

12 or 24 words; dice-only, machine-only, or combined. Mandated warnings for each mode are shown inline before you commit.

Collect & generate

Roll/flip or draw machine randomness; a single arm key generates — Enter is deliberately ignored so it cannot be triggered by reflex.

Write down & re-enter

The words are shown once; you type every one back with no echo. Only a full match continues — this catches copy errors before any funds exist.

Optional passphrase, then verify

Add an optional BIP39 passphrase, then confirm the fingerprint and addresses against your own wallet — and, if you want, open the optional watch-only / multisig export.

Scrub & power off

Secret material is overwritten and the machine powers down — no files, no logs, no network, nothing persisted by the application.

Entropy you can reason about

The seed provably follows only the entropy you saw or created.

An internal source audit traced the whole path — collection → conditioning → BIP39 → seed. The seed is a deterministic function of only your collected entropy plus fixed, declared constants: no hidden RNG, no timestamps, no environment values, and an empty transcript is refused at the cryptographic boundary. Machine randomness is fail-closed: RDSEED's success flag is honored on every draw and never substituted with zero, and the code refuses rather than proceed on an absent, timed-out, or stuck source — there is no weak software-RNG fallback anywhere.

Dice & coins

Entropy you can witness

Fair dice and coin flips, budgeted to a target strength, with an order-preserving transcript you can replay against the reference implementation.

Machine

Approved sources only

A compiled-in, versioned policy governs which hardware sources are allowed. True-random RDSEED is preferred; RDRAND can never stand alone.

Combined

Don't trust the silicon

Mix machine randomness with your own dice/coins. Your physical entropy is the backstop that does not depend on trusting the CPU's RNG.

The one thing it can't check: a CPU RNG that is subtly biased yet still passes the catastrophic checks. No software on that same CPU can detect it — which is exactly what Alea warns you before generation, and why dice/coin entropy exists. Read the entropy audit.

Getting it onto hardware

Download, verify, flash, boot — verify before you trust.

Download a release

Grab alea-x86_64-usb.img and SHA256SUMS from the releases page. Builds are reproducible from source.

Verify the checksum

Confirm the image matches SHA256SUMS before writing it. The release is unsigned by design at this stage — the checksum is how you verify it.

Flash the whole USB

Write the raw image to a USB device with Rufus (DD mode), balenaEtcher, or dd. It is a full GPT disk image.

Boot on real hardware

Disable Secure Boot (the payload is unsigned), boot the USB in UEFI mode. Alea refuses virtualization, so the full ceremony only runs on a real machine.

Rehearse first. A desktop rehearsal edition (public test vectors only, permanently watermarked, never a real generator) lets you practice every screen and mechanically cross-check the implementation against its reference before you ever use real entropy.

Security posture

Honest about the ceiling, not a marketing floor.

Alea's own stated limit is that it provides a small, auditable, pre-operating-system workflow that removes the desktop OS from seed generation and documents the firmware, hardware, release and physical trust assumptions that remain. It makes no claim to be unbreakable, trustless, or equivalent to a hardware wallet — those framings are permanently prohibited in this project, gates met or not.
